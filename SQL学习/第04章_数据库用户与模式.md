本章开始真正"建设"：创建学习用的用户 `student_pg`、数据库 `beginner_pg`、模式 `school`，并理解三者的所有权关系与搜索路径。

> 本章命令分**管理员会话**（`sudo -u postgres psql`）和**普通用户会话**（`psql -U student_pg -d beginner_pg`）两段，注意每段提示符。

## 4.1 先懂概念：角色（Role）= 用户 + 组

PostgreSQL 里没有单独的"用户"概念，统一叫 **角色（ROLE）**：

- **能登录的角色**（带 `LOGIN` 属性）= 日常说的"用户"；
- **不能登录的角色** = "组"，用来批量授权（[第 15 章](第15章_用户权限与安全.md)实践）。

```sql
CREATE ROLE student_pg LOGIN PASSWORD 'student_pg_2024';
--                    └─ 有 LOGIN 属性 → 可登录的"用户"
```

> ⚠️ **为什么示例用户叫 `student_pg` 而不是 `pg_student`？** PostgreSQL 把 `pg_` 前缀的角色名保留给系统角色（如 `pg_read_all_data`、`pg_monitor`），`CREATE ROLE pg_student` 会直接报错：
> ```text
> ERROR:  role name "pg_student" is reserved
> DETAIL:  Role names starting with "pg_" are reserved.
> ```
> 自建角色一律避开 `pg_` 前缀。

> 教程密码 `student_pg_2024` 仅用于练习。生产环境密码请长、随机、无规律，且永远不要写进代码里提交到 git。

## 4.2 创建数据库

数据库必须由**管理员**或有 `CREATEDB` 权限的角色创建。在管理员会话里：

```sql
postgres=# CREATE DATABASE beginner_pg
    OWNER student_pg          -- 归属 student_pg：它是这个库的"库主"
    ENCODING 'UTF8';          -- 字符编码：必选 UTF8，中文才不会乱码
```

关键点 **OWNER**：库主可以在这个库内建表、建模式、删掉整个库。把业务库交给应用账号而不是超级管理员，是基本的安全习惯。

其他常用操作：

```sql
postgres=# \l                              -- 查看所有库
postgres=# ALTER DATABASE beginner_pg RENAME TO study_pg;   -- 改名
postgres=# ALTER DATABASE beginner_pg OWNER TO other_role;  -- 换库主
postgres=# DROP DATABASE study_pg;         -- 删除库（不进回收站！里面数据全没）
```

> `DROP DATABASE` 前必做两件事：确认名字没拼错 + 确认连的不是这个库（不能删自己正连着的库），有其他会话连着它时 PG 会拒绝删除——这是最后一道保险。

## 4.3 创建模式

模式在**具体的数据库内部**创建。先连进 beginner_pg 再建：

```sql
postgres=# \c beginner_pg
beginner_pg=# CREATE SCHEMA school AUTHORIZATION student_pg;
--                                  └─ 归属 student_pg：它是模式所有者
```

现在层级搭好了：`beginner_pg` 库里有了 `school` 抽屉，抽屉归 `student_pg` 所有。

为什么要把表放进 `school` 而不是默认的 `public`？

1. 语义清晰：一眼看出 `school.students` 是"教学模块"的表；
2. 同库其他项目（比如以后加个 `library` 模式）互不干扰；
3. 可以按模式整体授权/回收权限（[第 15 章](第15章_用户权限与安全.md)）。

## 4.4 一键完成本章全部操作

上面三条可以合成一个脚本执行（`scripts/01_create_user_db.sql`，以管理员身份）：

```bash
$ sudo -u postgres psql -f scripts/01_create_user_db.sql
```

脚本内容核心就三句（外加幂等清理和授权细节）：

```sql
DROP DATABASE IF EXISTS beginner_pg;              -- 已存在则先删（重跑友好）
DROP ROLE IF EXISTS student_pg;
CREATE ROLE student_pg LOGIN PASSWORD 'student_pg_2024';
CREATE DATABASE beginner_pg OWNER student_pg ENCODING 'UTF8';
\connect beginner_pg                              -- 元命令：切进新库
CREATE SCHEMA school AUTHORIZATION student_pg;
ALTER ROLE student_pg IN DATABASE beginner_pg
    SET search_path = school, public;             -- 见 4.5，关键一步
```

## 4.5 搜索路径 search_path：为什么不用写 school. 前缀

完整表名是 `school.students`，但每次都写前缀太累。**search_path** 告诉 PostgreSQL"找表时按这个顺序找"：

```sql
beginner_pg=> SHOW search_path;
   search_path
─────────────────
 school, public          -- 4.4 的 ALTER ROLE 已设置好
```

效果：写 `students` 时 PG 先找 `school.students`（找到），找不到再找 `public.students`。

两种设置方式（作用域不同）：

```sql
-- 会话级：只影响当前 psql 会话，退出即失效
SET search_path TO school, public;

-- 永久级：绑定"某用户在某库"的默认（脚本 01 用的就是这种）
ALTER ROLE student_pg IN DATABASE beginner_pg SET search_path = school, public;
```

> 没设置 search_path 时默认是 `"$user", public`。这也是初学者 `relation does not exist` 报错的常见原因之一（表在 school 里，而搜索路径里没有）。

## 4.6 权限初体验（为第 15 章热身）

新建的 `student_pg` 现在拥有 `school` 模式，可以在里面建表。这里有一个反直觉的默认行为值得单独讲：

> **PostgreSQL 15 起，`public` 模式的 CREATE 权限从"所有人"收紧为"仅数据库所有者"**（PG 14 及更早是开放的，任何角色都能在 public 里建表）。这是安全改进，不是 bug。

**注意一个容易踩的细节**：因为我们是 `CREATE DATABASE beginner_pg OWNER student_pg`，`student_pg` 就是本库的**所有者**，因此它**在 public 里仍然能建表**：

```sql
beginner_pg=> CREATE TABLE public.t1 (id int);
CREATE TABLE                    -- 成功：student_pg 是 beginner_pg 的所有者
beginner_pg=> DROP TABLE public.t1;             -- 练习完删掉
```

真正会被 public 模式挡住的是**"不是本库所有者的普通角色"**（[第 15 章](第15章_用户权限与安全.md)会创建这样的只读账号）：

```sql
-- 以 ta_reader（非库主）连接时：
ta_reader=> CREATE TABLE public.t1 (id int);
ERROR:  permission denied for schema public   -- 这才是那条经典的权限报错
```

原因在于：PG 15 起 `public` 模式的所有者是特殊角色 `pg_database_owner`，它是**"当前数据库所有者"的占位符**——库主天然拥有 public 模式的全部权限，其他角色才需要显式授权。

**结论**：业务表放进自己的模式（如 `school`）始终是好习惯，但"库主在 public 里建不了表"是个常见误解。

## 4.7 查看：\l、\dn、\du

```sql
postgres=# \l          -- 数据库清单：名字 | 拥有者 | 编码 | 权限
postgres=# \dn         -- 模式清单（连到某库后执行）
postgres=# \du         -- 角色清单：名字 | 属性 | 成员关系
```

`\du` 输出里找 `student_pg`：属性列只有一行 `（无）`？不对——应该能看到它至少在 beginner_pg 的权限列出现。看角色属性详情用：

```sql
postgres=# \du student_pg     -- 只看这一个角色
postgres=# SELECT rolname, rolcanlogin, rolsuper FROM pg_roles WHERE rolname = 'student_pg';
```

- `rolcanlogin = t` → 能登录（有 LOGIN）；
- `rolsuper = f` → 不是超级管理员（好事，练习账号就该低权限）。

## 4.8 修改与删除用户

```sql
postgres=# ALTER ROLE student_pg PASSWORD '新的密码';      -- 改密码（最常用）
postgres=# ALTER ROLE student_pg CREATEDB;                -- 授予建库能力
postgres=# ALTER ROLE student_pg NOCREATEDB;              -- 收回
postgres=# DROP ROLE student_pg;   -- 删除角色：它必须先没有任何对象和权限，否则报错
```

> **删除角色的"依赖死结"**：角色一旦拥有过对象（库、模式、表），直接 DROP 会报 `role "student_pg" cannot be dropped because some objects depend on it`。练习环境最快的解法是先 `DROP DATABASE` 它名下的库；生产环境则要做对象所有权转移（`REASSIGN OWNED`，[第 15 章](第15章_用户权限与安全.md)）。

## 本章小结

- 角色是 PG 里用户与组的统一概念，`LOGIN` 属性决定能否登录；
- 三层建设：`CREATE DATABASE beginner_pg OWNER student_pg` → `\c` 进库 → `CREATE SCHEMA school AUTHORIZATION student_pg`；
- `search_path` 决定"不写前缀时去哪找表"，永久设置用 `ALTER ROLE ... IN DATABASE ... SET`；
- PG 15 起 public 模式的建表权限收紧为"仅数据库所有者"，其他角色需显式授权；业务表仍建议放自己的模式；
- `\l` 看库、`\dn` 看模式、`\du` 看角色。

骨架已就位（`beginner_pg` → `school`），下一章往模式里放第一批表，学习数据类型与约束。
