## 12.1 为什么需要事务

转账是教科书级的例子：A 给 B 转 100 元 = 两条 UPDATE（A 减 100，B 加 100）。如果第一条成功后突然断电、第二条没执行——100 元凭空消失。

**事务（Transaction）把多条 SQL 捆成一个"要么全成、要么全不做"的原子单元。**

事务的 ACID 四大特性（面试必考）：

| 特性 | 含义 | 通俗说法 |
|---|---|---|
| **A**tomicity 原子性 | 全部成功或全部回滚 | "一荣俱荣，一损俱损" |
| **C**onsistency 一致性 | 事务前后数据满足所有约束 | "账目永远平" |
| **I**solation 隔离性 | 并发事务互不干扰（程度可调） | "各干各的，像独占数据库" |
| **D**urability 持久性 | COMMIT 后的修改断电也不丢 | "落袋为安" |

## 12.2 基本操作：BEGIN / COMMIT / ROLLBACK

```sql
BEGIN;                                      -- 开启事务（也可写 BEGIN TRANSACTION; 或 START TRANSACTION;）

UPDATE school.students SET city = '测试市' WHERE student_id = 1;
SELECT name, city FROM school.students WHERE student_id = 1;   -- 此刻看到的是"已改"状态（未提交）

ROLLBACK;                                   -- 反悔：回到 BEGIN 之前
SELECT name, city FROM school.students WHERE student_id = 1;   -- 恢复原样

BEGIN;
UPDATE school.students SET city = '测试市' WHERE student_id = 1;
COMMIT;                                     -- 定案：不可再 ROLLBACK
UPDATE school.students SET city = '北京' WHERE student_id = 1; -- 手动改回去（练习数据）
```

**psql 的贴心细节**：事务里的提示符从 `beginner_pg=>` 变成 `beginner_pg=*>`——`*` 插在 `=` 和 `>` 之间，提醒你"手里有未提交的事务"。养成看到 `*` 就心里一紧的习惯。

三个事实：

1. **DDL 也能进事务**（PG 特色）：建表、删表同样可以回滚——MySQL 大部分场景不行，这是 PG 的一大优势；
2. 事务中报错的那条语句失效，但**事务还开着**；想干净退出用 `ROLLBACK`（或 `\r` 清掉未完成语句）；
3. **自动提交**：不写 BEGIN 时，每条语句自成一个微型事务，执行即提交——这就是为什么[第 6 章](第06章_数据的增删改.md)里"不带 WHERE 的 UPDATE"没有后悔药，而事务里可以 ROLLBACK。

> 日常防呆模板（[第 0 章](第00章_学习准备.md)承诺的咒语正式兑现）：
> ```sql
> BEGIN;
> -- 危险的 UPDATE/DELETE
> -- SELECT 检查影响范围
> COMMIT;   -- 或 ROLLBACK;
> ```

## 12.3 并发事务：两个会话的实验（本教程最有趣的实验）

开**两个** psql 窗口（或 psql + pgAdmin 两个 Query Tool），都连 student_pg。下文记为会话 A / 会话 B。

### 实验 1：READ COMMITTED（PG 默认隔离级别）下的可见性

```text
会话 A                                会话 B
──────────────────────────          ──────────────────────────
BEGIN;
SELECT city FROM school.students
 WHERE student_id = 2;   → '上海'
                                     BEGIN;
                                     UPDATE school.students
                                      SET city = '魔都'
                                      WHERE student_id = 2;
SELECT city FROM school.students
 WHERE student_id = 2;   → '上海'   ← A 仍看到旧值（B 未提交）
                                     COMMIT;
SELECT city FROM school.students
 WHERE student_id = 2;   → '魔都'   ← A 在同事务内看到了新值！
COMMIT;
```

**READ COMMITTED 的语义**：每条语句开始时拍一张最新快照——所以同一个事务里两次读，可能读到不同结果（"不可重复读"）。这是 PG 默认行为，简单高效，绝大多数应用够用。

> 顺手把数据改回去：`UPDATE school.students SET city='上海' WHERE student_id=2;`

### 实验 2：写冲突与行锁

```text
会话 A                                会话 B
──────────────────────────          ──────────────────────────
BEGIN;
UPDATE school.students SET city='A市'
 WHERE student_id = 3;
                                     BEGIN;
                                     UPDATE school.students SET city='B市'
                                      WHERE student_id = 3;
                                     （卡住不动……B 在等 A 释放行锁）
COMMIT;
                                     UPDATE 1（B 解除阻塞执行）
                                     COMMIT;      → 最终 city='B市'（后写覆盖）
```

**规则**：UPDATE/DELETE 会给目标行**加锁**，另一个事务改同一行必须等。PG 默认不设 `lock_timeout`，会话 B 会一直等下去（需要上限就 `SET lock_timeout = '5s';`）；而**死锁**（A 锁行 1 等 B 的行 2，B 锁行 2 等 A 的行 1）会在约 1 秒（`deadlock_timeout`）被自动检测，被牺牲的一方报：

```text
ERROR: canceling statement due to statement timeout
-- 或死锁场景（双方互相等对方）：
ERROR: deadlock detected
DETAIL: Process 1234 waits for ShareLock on transaction 5678 ...
```

**死锁**（A 锁行 1 等 B 的行 2，B 锁行 2 等 A 的行 1）时 PG 会自动检测并**牺牲一个事务**（报错回滚它），另一个继续。程序里应捕获死锁错误并重试。

### 实验 3：REPEATABLE READ——同一事务内读数恒定

```text
会话 A                                 会话 B
──────────────────────────           ──────────────────────────
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT city FROM school.students
 WHERE student_id=2;   → '上海'
                                      UPDATE school.students
                                       SET city='花城'
                                       WHERE student_id=2;   （自动提交）
SELECT city FROM school.students
 WHERE student_id=2;   → '上海'      ← 仍是旧值！快照固定在 BEGIN 那一刻
COMMIT;
SELECT city FROM school.students WHERE student_id=2;
                       → '花城'      ← 事务外才能看到
```

**REPEATABLE READ 的语义**：事务开始时拍快照，之后读数一致（"可重复读"）；但代价是——若你在事务中要**修改**一个别人已改的数据，会报：

```text
ERROR: could not serialize access due to concurrent update
```

这时只能 ROLLBACK 重来（不能原地继续）。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 适用 |
|---|---|---|---|---|
| READ UNCOMMITTED | （PG 不支持，等同下一档） | | | — |
| **READ COMMITTED**（默认） | 不可能 | 可能 | 可能 | 90% 场景 |
| REPEATABLE READ | 不可能 | 不可能 | PG 下也不可能* | 报表、一致性读取 |
| SERIALIZABLE | 不可能 | 不可能 | 不可能 | 最严格，冲突多需重试逻辑 |

\* PG 的 REPEATABLE READ 实现基于快照隔离，比标准更严格。级别在 BEGIN 时指定：`BEGIN ISOLATION LEVEL REPEATABLE READ;`，或看当前级别：`SHOW transaction_isolation;`

## 12.4 SAVEPOINT：事务里的"存档点"

长事务里做完一步存个档，后面错了不必全部重来：

```sql
BEGIN;
UPDATE school.students SET city = '测试A' WHERE student_id = 4;
SAVEPOINT sp1;                          -- 存档
UPDATE school.students SET city = '测试B' WHERE student_id = 5;
SELECT city FROM school.students WHERE student_id IN (4,5);   -- 看看两个改动
ROLLBACK TO sp1;                        -- 只撤销到存档点：5 的改动撤销，4 的保留
SELECT city FROM school.students WHERE student_id IN (4,5);
COMMIT;                                 -- 最终只有 student_id=4 的改动生效
```

应用场景：批量导入 1 万行，第 6000 行出错——SAVEPOINT 分批存档，从断点重跑而不是从零重来。

## 12.5 锁的家族（概念篇，够用版）

| 锁 | 谁持有 | 影响 |
|---|---|---|
| 行锁（RowExclusive） | UPDATE/DELETE 目标行 | 其他事务改同一行需等待 |
| 表锁 | `LOCK TABLE 表 IN ... MODE;` 显式加 | 按模式限制他人读写 |
| MVCC（多版本并发控制） | 所有读者 | **读不阻塞写、写不阻塞读**——PG 高并发的根基 |

MVCC 一句话：修改会创建数据行的**新版本**，读者按事务快照选版本看，所以读写互不挡路（实验 1 中 A 读旧值、B 写新值，正互不干扰）。代价是旧版本需要清理——那就是 `VACUUM` 的工作（[第 13 章](第13章_索引与EXPLAIN.md)末尾提）。

排障工具：锁住了想知道谁锁的？管理员会话里查 `pg_locks` / `pg_stat_activity` 视图：

```sql
SELECT pid, state, wait_event_type, query
FROM pg_stat_activity
WHERE datname = 'beginner_pg';         -- 看谁在跑什么、谁在等
-- 卡死的会话可以由管理员终结：
-- SELECT pg_terminate_backend(pid);
```

## 本章小结

- 事务 = 原子单元，BEGIN → 操作 → COMMIT（定案）/ ROLLBACK（反悔）；psql 提示符多 `*` 表示有未提交事务；
- ACID：原子、一致、隔离、持久；DDL 在 PG 里同样可回滚；
- 不写 BEGIN 的语句自动提交——这就是危险操作要手动包事务的原因；
- 默认 READ COMMITTED（每语句一快照）；REPEATABLE READ（整事务一快照，写冲突需重试）；死锁自动检测牺牲一方；
- SAVEPOINT 事务内存档；MVCC 让读不阻塞写；`pg_stat_activity` 是排查卡顿的第一现场。
